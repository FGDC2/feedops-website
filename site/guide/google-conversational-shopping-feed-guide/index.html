Prepare product data for conversational Shopping.

Conversational shopping experiences depend on product information that Google can understand and verify. This guide explains how FeedOps can map configured client data into validated conversational attributes while preserving reliable feed behaviour.

Start with the product data you already own.

FeedOps is designed to extend an existing product-feed workflow. The goal is not to replace a client’s feed or invent unsupported information. It is to apply approved mappings and validation rules so eligible product context can be represented consistently and reviewed before rollout.

Important: richer product information can help Google understand products, but it does not guarantee rankings, traffic, inclusion, or visibility in any particular conversational experience.

Six attributes in the initial FeedOps scope.

question_and_answer

Product-specific questions and answers that add useful context.

document_link

Approved links to relevant product documentation or supporting content.

related_product

Configured relationships to complementary or alternative products.

item_group_title

A shared title or theme for products in the same group.

variant_option

The option represented by a product variant, such as size or colour.

popularity_rank

A configured ranking signal with an agreed scale and freshness expectation.

Implementation flow

Map, validate, review, then pilot.

  1. Confirm the client’s use case and choose the attributes that have trustworthy source data.
  2. Inventory source fields, content, links, relationships, variants and ranking inputs.
  3. Apply the approved mapping, eligibility, precedence and fallback rules.
  4. Generate representative input/output examples and review them with implementation and product stakeholders.
  5. Run audit and regression checks before a controlled pilot.
  6. Monitor output quality during rollout and expand only after review.

Validation first

Safe degradation is part of the design.

Optional conversational attributes should not make existing feed generation fail. Missing, invalid, conflicting, duplicate or out-of-range values need explicit rules. Depending on the attribute, the correct outcome may be a normalised value, a safe fallback, or omission with an audit trail.

  • Keep output deterministic and explainable from configured source data.
  • Do not guess missing product facts.
  • Confirm URL, product identity, relationship and range checks for the relevant attribute.
  • Keep unresolved edge cases as review items until the mapping specification is approved.

Evidence

Use examples that show the full path.

Each example should show source input → mapping or rule → generated attribute → validation or audit result → customer-facing explanation. Publish examples only after engineering or implementation confirms that they match the current pipeline behaviour.

Useful examples include a complete product, a variant set, a related-product relationship, a grouped product set, a ranking value, and a missing or invalid value that is safely omitted.

Readiness checklist

Before you roll out.

  • Source fields and ownership are confirmed.
  • All six mappings have approved eligibility and fallback rules.
  • Representative output has passed product and implementation review.
  • Audit and regression evidence is available.
  • Pilot scope, success measures and escalation path are agreed.
